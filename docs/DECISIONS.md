| 2026-10-09 | `spring.ai.openai.base-url` default includes `/v1` (`…:1234/v1`) | Spring AI 2.x appends only `/chat/completions`; without `/v1` LM Studio answers 200 + `{"error":…}` and the SDK fails with `` `choices` is not set `` (M7) |

| 2026-10-09 | CV text truncated to 15,000 chars before the LLM call | Combined prompt must fit the local model's context window; posting is already capped at 20,000 by validation (M7) |
| 2026-10-09 | PDF rendering done directly with PDFBox 3, not openhtmltopdf/Thymeleaf | openhtmltopdf 1.0.10 pins PDFBox 2.0.24, which conflicts with the PDFBox 3.x used for extraction; rendering with PDFBox 3 + embedded DejaVuSans keeps one PDFBox version and still yields selectable text with full Polish charset (plan §6.8 allows OpenPDF-style alternatives; M9) |
| 2026-10-09 | Pipeline split into an interface with a conditional implementation: `cvchecker.pipeline.mode=real` (default) vs `=simulated` | The SSE integration tests need the staged sleep pipeline without a local LLM; the app runs the real PDFBox→LLM→render pipeline by default (plan §6.7 vs M4 acceptance, M10) |
| 2026-10-09 | Per-job model override passed to the LLM services via `OpenAiChatOptions` (model + temperature 0.2) | The frontend model dropdown must actually steer which LM Studio model runs; blank selects the `LLM_MODEL` default (M7 extension) |
| 2026-10-09 | `max_tokens` set to 8192 explicitly (default 4096) | LM Studio truncates structured output at the client's default cap; reasoning models such as gemma-4-e4b additionally burn hundreds of completion tokens on hidden `reasoning_tokens` before emitting the JSON — without a generous budget the rewrite JSON gets cut mid-object (`LLM_INVALID_OUTPUT`) |
| 2026-10-09 | Structured output via `response_format: json_schema` (strict), wired through `OpenAiChatModel.ResponseFormat` | LM Studio enforces the schema at generation time, so the response cannot be structurally invalid — this fixed gemma-4-e4b's consistently unbalanced rewrite JSON (`}]}` missing a closer, balance −1). Only JSON-schema mode reliably works with small reasoning models; prompt-only JSON elicitation does not. Validation + 3 attempts with a corrective hint remain as the safety net (plan §6.7, docs/ENVIRONMENT.md). Schemas live in `prompts/analysis.schema.json` and `prompts/rewrite.schema.json` |
| 2026-10-10 | Model dropdown is a global LM Studio switcher, decoupled from job submission | Selecting a model calls the new `POST /api/llm/models/load` (native LM Studio `/api/v1/models/load`); the selection persists until changed. `POST /api/cv-jobs` no longer carries a `model` field — jobs run on whatever LM Studio has loaded at analysis time, defaulting to `LLM_MODEL` (docs/API.md §1/§6) |
| 2026-10-10 | The CV is a single persistent resource: `POST /api/cv` stores it once, `POST /api/cv-jobs` references it by `cvId` | Removes the need to re-attach the same PDF for every posting. Only one CV is kept (not file history — out of scope): a new upload replaces it, deleting the old file. Each job copies the CV bytes at creation, so a replacement never affects a queued/running job. The frontend restores the selection from `localStorage` + `GET /api/cv/{cvId}` after a refresh (docs/API.md §1/§7) |
| 2026-10-10 | Model switch unloads-then-loads: `POST /api/llm/models/load` first unloads every currently loaded instance in LM Studio (native `POST /api/v1/models/unload`, ids from `GET /api/v1/models` + the last instance the app loaded) before loading the new one | LM Studio holds a single model in memory; loading another while one is loaded fails with OOM. Unloading **all** loaded instances before each load (best-effort) also avoids instance leakage when reloading the same model — LM Studio increments instance ids per reload (`model:1`, `model:2`, …) and untracked/older instances would otherwise linger forever. Embedding instances are included: they are tiny and reload on demand. |
| 2026-10-12 | Model status endpoint `GET /api/llm/models/loaded` (reachable + loaded model keys) drives a status line and gates **Submit** | A job cannot run without a model in memory, so the frontend disables Submit until LM Studio answers with at least one loaded model; the status line shows "no model loaded / LM Studio unavailable / loaded: X" and is refreshed on load attempts and every 15 s while the form is open (docs/API.md §6.1) |
| 2026-10-12 | Job history moved from browser `localStorage` to a backend JSON file (`JobFileStore`, newest 20; `StoredJob` record + Jackson → type-safe) | The user restarts the backend and still wants the queue visible; `localStorage` was the browser-only workaround. `InMemoryCvJobRegistry` persists on create/remove/every stage change and restores on startup (marking jobs that were running as `FAILED`/`INTERRUPTED`, since their temp files are gone). New `GET /api/cv-jobs` (list) and `DELETE /api/cv-jobs/{jobId}` (Dismiss) back the UI; `JobSnapshot` gained `fileName`. Metadata only — no CV/posting text or PDFs on disk (docs/API.md §8) |
| 2026-10-12 | **Workspace redesign**: the app becomes a workspace around a persistent CV + model context. Old `/api/cv-jobs*` endpoints are deprecated; new contract in docs/API.md (persistent CV §2, model context §3, analyses §4, single SSE §7). The `job` domain (CvJob/Stage/JobReport/etc.) is replaced by an `analysis` domain; old endpoints, pipeline and frontend pages are removed in the final milestone | A per-job streaming model, localStorage id persistence and a form that asks for everything each time no longer fit the target UX; one SSE connection per tab removes the browser per-domain connection limit that stuck cards on "Reconnecting…" |
| 2026-10-12 | Analyses live in a **pure in-memory registry**; the `JobFileStore` disk persistence is dropped | Task scope explicitly: backend restart → empty registry, frontend silently drops unknown ids. Persistence, if wanted later, goes behind the registry interface — not part of this iteration |
| 2026-10-12 | Analysis registry keeps a **snapshot of the CV text** (and file name) per analysis, taken at creation | Replacing the CV must not affect existing analyses; re-reading text lazily from a replaced file is impossible |
| 2026-10-12 | `POST /api/cv` extracts text immediately and **rejects scans** (`PDF_NO_TEXT` / `PDF_UNREADABLE` → 422, previous CV stays) | The workspace CV must be usable by the pipeline; never store an unusable active CV |
| 2026-10-12 | Model `ready` = active id set + model has a loaded instance in LM Studio **and** answers a 1-token chat probe | "Loaded and answering" per spec; the probe is cheap and separates dead-loaded from usable-loaded. Unreachable LM Studio → `ready:false` + `reason`, never a crash |
| 2026-10-12 | Model switching semantics: analyses record the active model at creation; a switch during an in-flight LLM call can abort it (`LLM_ABORTED`, retry after the switch); awaiting/completed analyses are unaffected | LM Studio hosts exactly one loaded model, so mid-call unload is the only way to switch; documenting it lets the UI warn and the user decide (docs/API.md §6.3) |
| 2026-10-12 | The single SSE stream uses **global event ids**, a bounded replay buffer (default 1000 events) and `ping` heartbeat; `analysis.updated` carries the analysis summary only, and the client re-fetches detail on significant transitions | Keeps payloads small; detail is cheap to fetch locally and always consistent; bounded buffer bounds memory while covering reconnect gaps |
| 2026-10-12 | API changes to LLM records: `CvAnalysis` gains `employer`/`position` and becomes `Evaluation`; `Suggestion` becomes `(id, section, problem, proposal, before, after, priority)` | Title extraction (`Employer · Position`) and the review UI (checkbox + before/after + priority) need these fields; the LLM schema files are updated with them |
| 2026-10-12 | `GlobalEventStream`: a connect without `Last-Event-ID` is live-only (no replay); `ping` frames get a global id but are never buffered/replayed; a malformed `Last-Event-ID` is treated as live-only; heartbeat reuses `cvchecker.sse.heartbeat-interval` | The client already loaded full state over REST on a fresh connect, so replaying history would duplicate it; pings carry no state and must not fill the replay buffer; reusing the existing interval avoids a second near-identical setting (M4) |
| 2026-10-12 | Frontend redesigned as a workspace: `CvContextStore` + `AnalysesStore` + `ToastStore` signals, one `EventsService` `EventSource('/api/events')` for the whole app, plus components per the target UI (`AppShell`, `TopBar`, `CvChip`, `ModelSelect`, `AnalysisSidebar`, `AnalysisDetail`, `SuggestionList`, `NewAnalysisForm`, `CvDropzone`) |
| 2026-10-12 | Frontend no longer stores CV references or job ids in `localStorage`; the backend is the source of truth, `GET /api/cv` 404 means "no CV" (a normal answer, not an error), and unknown analysis ids are dropped silently |
| 2026-10-12 | CV/model state seeding and suggestion defaults are test-only helpers in `frontend/src/app/testing/workspace.ts`; store specs seed the two construction requests deterministically instead of depending on request ordering |
| 2026-10-12 | Old workspace removed: `CvJobController`/`job` package, `pipeline` package, per-job `SseHub` + `StatusData`/`CompletedData`/`FailedData`, and the deprecated `POST /api/llm/models/load` + `GET /api/llm/models/loaded` endpoints (docs/API.md §3) |
| 2026-10-12 | CV + model TTL config keys renamed `cvchecker.jobs.*` → `cvchecker.analyses.*`; `AnalysisTtlCleanup` replaces the job `TtlCleanup` (terminal analyses only, broadcasts `analysis.deleted`) |

| 2026-10-14 | Added `cv.updated` to the single SSE stream (empty `data`; the client re-fetches `GET /api/cv`) | The plan's event list omitted it, but "two browser tabs stay in sync" also covers the CV chip: replacing the CV in one tab now refreshes the others (docs/API.md §7) |
